## 素材瘦身：包体 317MB → 134MB（2.37x）

起因：用户问「卡池增加需要增加新立绘吗」。查账发现 46 张卡（45 卡 + 先机虎符）**100% 有立绘、零缺图**，扩到 70 张 = +24 张图 ≈ +75MB。用户选择「先瘦身，再决定扩不扩」；新卡方向定为**关键词联动**（记在 next-steps 1.1）。

### 诊断：包大不是因为内容多
- 74 个 `.import` 全是 `compress/mode=0`（无损原样），200MB 立绘原封不动进包；
- 字体两个字重 42MB（比所有卡图加起来还多），全量中文字库塞进去只用 950 字。

### 做法
1. **纹理**：`compress/mode=0→1`（WebP 有损），`lossy_quality=0.7→0.8`。74 张 200MB → 27MB。
   - 单图 PSNR 36dB；整屏实测 `_gd-menu` 39.8dB / `_gd-codex-cards` 43.8dB，可见差异像素 0.03%~1.4%。
   - 误差分布图确认：误差集中在轮廓/草叶边缘（人眼掩蔽），平坦背景干净，无色带。
   - 极端对照 q0.30 只把整屏降到 36.6dB → 这批水墨图对 WebP 极不敏感，q0.8 是安全的中间档。
2. **字体**：新建 `tools/subset-fonts.py`，扫 `godot/**/*.gd` 字符串字面量（跳过注释）+ `data/*.json` + `js/*.js`，取 1394 个汉字（其中实际会显示 950 个）做子集。47.7MB → 1.8MB。
   - **源字体移到 `assets/fonts-src/`（Godot 工程之外）**，否则 `all_resources` 会把 47MB 源文件也打进包，子集化白做。
   - `godot/fonts/` 保留同名文件，`UiTheme` 按 `res://fonts/NotoSerifSC-*.otf` 加载，代码零改动。
   - 新增 `godot/tests/fonts_test.gd`（2 项）：扫源码全部字符串字符 vs `FontFile.get_supported_chars()`，漏字报红并提示重跑脚本。这是防"以后加文案出豆腐块"的守卫。

### 踩坑
- **改 `.import` 不 `--import` 等于没改**：读的还是旧 ctex。判断依据看 ctex 字节数（253554 → 114256 才是真变了）。
- **拿错文件做对比差点得出"压缩无效"的假结论**：`--tour` 只重出它自己的 19 张，`_gd-battle.png` 是历史遗留、巡览根本不截，于是 md5 三次完全相同。正解是 grep `[tour] 截图` 的实际清单。已写进 technical 踩坑 32。

## 1.2 死战专精（Build 靠卡堆成立）

**先量成因，再动手**——这是这轮最重要的方法。11.5 假设"浓度到不了阈值"，实测相反：
专精玩家已经拿到 7.6 张死战牌、浓度 27%，通关只比随机高 3.5pp。所以问题是
**"选了没用"**（每张只值 1~2 点属性），不是"选不到"。这一步顺手否掉了
"精英关发两张"和"定向奖励"两条路（都在白给强度）。

- 机制：牌组里死战牌**占比** 20%/25%/30% → 死战召唤的援军 +0/+1、+1/+1、+2/+2。
  只对 `ctx.lastStand` 的召唤生效（战吼召唤不吃），只对 p1 生效。
  `campaign.engineRules` 注入 `rules.lastStandAtk/Hp/Tier`，引擎只认数字，档位表与引擎解耦。
- **口径必须是占比不是张数**：牌组 20→28 张，张数门槛会随规模漂移（早期 6 张=30%，
  晚期 6 张=21%）。试过三套张数门槛全部作废：4/6/8（太松，质量流也吃到 → 死战 28%/随机 17）、
  7/9/11（太紧，专精只有最后两关生效 → 9%）、6/8/10 + 幅度递增（军师叠加 38%）。
- 实测：死战 7%→13%（+6），质量流 12%→14%，随机 7%→9%。**死战从"明显更差"变成"能玩"**。
- 遗留：军师叠加 28~29%（超 23% 上限），但"韩信+质量流"也 28%——是 1.1 遗留的韩信偏强，
  下一刀 `ADV_HANXIN_COUNT` 2→1。
- 新增诊断脚本：`test/diag-reward.js`（刷出率 vs 拿取率）、`test/diag-tier.js`（三种策略浓度分布）。
- 验收：全量 **1469 项 + E2E 19** 全绿（replay 564 / campaign 133 / i18n 187）；
  地图新增常驻 chip「死战专精 +X/+Y」（中英双份），战报「增援抵达前锋列（死战专精 +1/+1）」。

## 顺手修的旧 bug：Label 的 size 被文本顶回（TextureRect 同款坑第二次）

英文卡名最长 29 字符（General · Warlord of the Dead），卡名条 124 宽根本放不下，
原来直接画出卡外压到邻牌。**真因不是字号，是顺序**：Label 的最小尺寸 = 整句文本宽度，
`size = Vector2(124,28)` 被顶回 230；而 `clip_text = true` 时最小尺寸才是 0 →
**必须先开 clip_text 再 set_size**，反了等于没开。

我一开始只在后面加 `text_overrun_behavior`，截图看不出任何变化，打印才发现
Label.size 是 (230,28) 而不是 (124,28)。和 11-03 早些时候的 TextureRect 是同一个坑，
换成 Label 又来一次。**判据：任何「限制尺寸」的 Control，先查它有没有 minimum_size 顶着。**

另外字号不能按字符数猜（中文 1em、英文 0.5em），改成 `Font.get_string_size()` 实测，
下限 8 号（29 字符在 9 号要 131px，8 号 116px 刚好放下）。

测试加进 `art_rect_test`（25 → 30）：断言卡名 Label 的 size 不被顶回、最长英文名
在该字号下真的放得下、中文短名仍是 14 号（不误伤）。
全量 1857 → **1862 项 + E2E 19**。
